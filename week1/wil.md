**도메인 리팩터링**
잘 돌아가는 코드보다는 "고치기 쉬운 코드"에 중점
리팩터링 : 프로그램의 겉보기 기능이나 외부 동작을 바꾸지 않으면서(기능적 동등성을 유지하며) 내부 코드의 구조와 디자인을 개선하는 작업

**예시 코드에서의 문제**
1. service 계층에 많은 작업이 몰려있음(재고 확인, 물품 상태 확인, 상태 변경 등) -> "entity의 규칙은 entity가 책임지게 하자"
2. 기존 구조에서 @Setter로 인한 우회로 발생(검증 거치지 않고 물품 등록 가능)

**리팩터링을 통해 얻고자 하는 효과**
1. 우회로 차단
2. 구조 개편 -> 검증 코드 entity에만 존재 -> 요구사항 변경 발생 시 코드 한군데만 변경하면 됨

**테스트 코드**
단위 테스트 : 코드적인 알고리즘만 테스트 → db 연결 등의 조작 필요없음 → 빠름
통합 테스트 : 실제 서비스 운영 시를 기준으로 잘 동작하는지 확인 (db 연결, 매핑 등도 확인) → 비교적 느림

**TDD(Test-Driven Development, 테스트 주도 개발)**
실제 코드를 작성하기 전에 테스트 코드를 먼저 작성하는 모범적 소프트웨어 개발 방법론으로, 작은 단위의 설계를 짧은 주기로 반복하며, 개발 프로세스를 확실하고 안정적으로 유지하는 데 초점을 둠
Red(실패하는 테스트 작성) -> Green(성공하는 테스트 작성) -> Refactor(코드 가독성 및 구조 개선)라는 3단계 순환 과정을 매우 짧은 주기(수 분 단위)로 반복
장점 : 테스트가 디딤돌 역할을 하여 코드 수정 시 side-effect를 즉시 감지, 테스트 코드 자체가 시스템의 동작 방식을 설명하는 구현 명세서 역할을 함, 테스트하기 쉬운 코드를 고민하다 보면 자연스럽게 결합도가 낮고 응집도가 높은 설계가 도출됨
단점 : 스트 코드를 먼저 작성해야 하므로 초반 구현 시간이 약 1.5~2배 늘어남, 비즈니스 로직이 자주 변경되면 테스트 코드도 함께 대폭 수정해야 함, 테스트하기 좋은 코드를 설계하는 감각과 프레임워크 숙련도가 필요

// 리팩터링의 효과를 보기 위해서는 테스트 코드를 리팩터링 이전에 **반드시** 작성해두어야 함
테스트 코드의 구조 : given(이러한 상황에서~), when(~ 한다면), then(~ 되어야 함)
